## Build decisions

## Design system derived from agreed Brand/ mockups — 2026-10-21

**Decision:** Created `DESIGN_SYSTEM.md` + `design/tokens.css` as the canonical visual/interaction system, derived from the four product-owner-approved mockup screens in `Brand/CareNav AI App Walkthrough Screens.png` and the logo in `Brand/CareNav AI Heart Chat Logo.png`. Color tokens were extracted by pixel-sampling those PNGs (via a PowerShell/System.Drawing script, no Figma/export file exists), not re-designed from scratch. Motion/interaction guidance layers the `apple-design` skill on top of the static mockups.
**Why:** the user explicitly asked for a design system to build the UI from, following the agreed designs rather than a freshly invented style.
**Affects:** all future UI work across every epic; `CLAUDE.md` now points to `DESIGN_SYSTEM.md` as required reading before UI tasks.
**Alternatives considered:** waiting for an exact-hex design-tool export before building a tokens file — rejected because it would block UI work with no scheduled source for that export; documented as an open item (DESIGN_SYSTEM.md §10) instead, to be reconciled later if exact values are supplied.

## T-01 scaffold choices — 2026-10-21

**Decision:** Next.js 16.4 (App Router), React 19, Zod 4, OpenAI SDK 7, pino 10, Vitest 5. TypeScript pinned to `~6.0` (not 7.x) because typescript-eslint supports `<6.1`. New env vars not named in CONTEXT.md §11: `SHOW_DRAFT_LABEL` (FR-29 switch, default `true`), `RATE_LIMIT_PER_MINUTE` / `RATE_LIMIT_PER_DAY` (the `RATE_LIMIT_*` placeholder), `LOG_LEVEL`. Model names in `config/models.json` and prices in `config/pricing.json` are **untested/unverified placeholders** — each file says so, pending model evaluation and a pricing-page check. The logger exposes no free-text message argument at all; strings in allowed fields must look like short identifiers or are replaced with `[dropped]`.
**Why:** stable toolchain for a tight deadline; FR-29 needs a config switch; rule 8 is easier to keep if the logger cannot accept content.
**Affects:** `package.json`, `.env.example`, `config/*`, `src/lib/config/*`, `src/lib/log/logger.ts`.
**Alternatives considered:** TypeScript 7 (breaks linting); per-call message strings in logs (rejected — content leak path).

## T-02 database access without an ORM — 2026-10-21

**Decision:** better-sqlite3 with plain numbered SQL migrations (`src/lib/db/migrations/NNN_*.sql`) and a ~30-line runner. No Drizzle/Kysely. New env var `DATABASE_PATH` (default `data/carenav.sqlite`, gitignored).
**Why:** eleven small tables and prepared statements don't need an ORM. Plain SQL is easiest to review and port to Postgres for the pilot.
**Affects:** `src/lib/db/*`, FR-14/15/16 storage.
**Alternatives considered:** Drizzle (CONTEXT.md §4.4 default). Rejected for now as extra surface for no gain at this size; revisit if queries grow.

## Gate and pipeline shape — 2026-10-21

**Decision:** (1) Every rules list (en, jam, pcm, stroke) runs on every input regardless of language hint; child rules also trigger on text mentioning a baby/young child. (2) Gate level order emergency > crisis > urgent > uncertain > clear (emergency-vs-crisis precedence is an open clinical question). (3) Moderation maps flagged self-harm to `crisis` and self-harm score ≥ 0.2 to `uncertain` (DRAFT thresholds). (4) PRD 9.8 English second pass is skipped only when the level is already `emergency`. (5) Generate routes return `{kind:"urgent", gate}` with no AI text when not clear, unless `continue_after_ack` and the request says the user acknowledged; results carry `meta.urgentAcknowledged` for the persistent banner. (6) The derived user version is always produced (simple English even for English input, per AC-01.7); on parity/protected-span failure the result has `user: null` and the UI shows English only with a notice. (7) Grounding fuzziness only tolerates near-identical words and droppable short fillers — never digits, negations or swapped words. (8) New env `MAX_LETTER_CHARS` (6000) since letters are longer than typed answers.
**Why:** fail-closed and "most cautious wins" per CLAUDE.md rules 1-3; code-switching makes per-language rule selection unsafe; fuzzy grounding must never let an invented dose through (rule 7).
**Affects:** `src/lib/safety/*`, `src/lib/ai/pipeline/*`, `src/lib/validate/*`, `src/app/api/*`.
**Alternatives considered:** selecting rule lists by detected language (misses code-switching); character-level fuzzy grounding (let changed doses through in long quotes — caught by tests).

## T-09 guided-step UI choices — 2026-10-21

**Decision:** (1) Step 4 "Changes and patterns" isn't optional (AC-21.2 names only steps 5 and 6), so it accepts text *or* an "I haven't noticed any pattern" tick rather than forcing the user to invent something. (2) Step 1 asks for an age band only for "My child" (AC-09.3); "Someone I look after"/"Someone else" get an optional free-text "who are they to you?" label, which is screened like any other free text. (3) Step 3 makes both pickers required, each with an "I'm not sure" option. (4) Optional steps relabel the primary button "Skip this step" while empty instead of adding a second button. (5) Every submit screens *all* unscreened free text in state, not just the current step's, so text edited and then left via Back can't reach Review unscreened. (6) Filled coral/teal button labels are 19px bold (not the 16px/600 `--text-button`) so white-on-coral meets the large-text contrast threshold. (7) Step transitions use the View Transitions API with a `linear()` spring curve (new `--ease-spring-default` token), so no animation library is added.
**Why:** keeps to the AC wording without forcing false answers; keeps the "no unscreened text proceeds" invariant simple; satisfies DESIGN_SYSTEM.md §2's contrast note; avoids a new dependency.
**Affects:** FR-21, FR-09, FR-06, `src/lib/prepare/state.ts`, `src/components/prepare/*`, `src/components/ui/Button.module.css`, `design/tokens.css`.
**Alternatives considered:** making step 4 optional (contradicts AC-21.2); asking an age band for every "someone else" (more friction, not in AC-09.3, flagged to the product owner instead); Motion/Framer Motion for springs (new dependency for one transition).

## Result layout: list by default, card deck as an option — 2026-10-21

**Decision:** Results stay a scrolling list by default. A toggle ("Go through it one card at a time") switches the user's own version to a swipeable card deck (`src/components/ui/CardDeck.tsx`): spring physics, 1:1 tracking, interruptible, rubber-band ends, flick projection, plus Next/Back buttons, arrow keys and a "2 of 6" counter as equal alternatives; cards scroll internally at large text sizes; cross-fade under reduced motion. The urgent banner and DRAFT label stay pinned outside the deck; "Unclear or missing" and "We couldn't find this" are never only at the back of the deck; the clinician (English) tab and the PDF are always a list. The toggle remembers the choice on that device.
**Why:** product owner accepted the recommendation: a deck helps calm one-at-a-time reading, but as a default it hides safety-relevant sections, slows a clinician scanning the result, and is harder for screen-reader, low-dexterity and large-text users.
**Affects:** `src/components/ui/CardDeck.*`, `src/lib/ui/spring.ts`, both result views (wired once the Journey 2 result lands).
**Alternatives considered:** deck as default (rejected for the reasons above); deck default on the user tab only (offered as a middle ground, not chosen).

## Breathing: can't breathe = emergency, difficulty = urgent — 2026-10-21

**Decision:** Product owner: "inability to breathe is an emergency, breathing difficult is urgent." Emergency keeps: can't breathe / can't catch breath, not breathing, choking, gasping or fighting for breath, blue or grey lips. Urgent (new `*.breathing.difficult` rules, en/jam/gyn/trf/ht/pcm; hi and tw already had them): struggling to breathe, difficulty or trouble breathing, hard to breathe, short of breath, breathless. Negated letter wording ("denies shortness of breath") doesn't fire. Unchanged: chest pain with breathlessness (emergency via the chest-pain rule), and child rules (a baby or child under 5 struggling to breathe is still emergency). Gate classifier prompt bumped to v2 to match.
**Why:** product-owner answer to the open clinical question.
**Affects:** `content/urgency-rules/*`, `src/lib/ai/prompts/gate-classifier.v2.md`, `tests/urgency/rules.test.ts`.
**Alternatives considered:** treating gasping / fighting for breath as urgent (they describe barely getting air, so kept with "can't breathe" — flagged to the product owner).

## T-23 accounts: password, magic link, sessions, invites — 2026-10-22

**Decision:** (1) Passwords: argon2id via `@node-rs/argon2` with its defaults (19 MiB, 2 passes; Node 22 has no built-in argon2), at least 10 characters, generic errors ("That email and password don't match"); login always runs a verify (against a dummy hash when there is no account or no password) so timing doesn't reveal which emails exist. (2) `/api/auth/{register,login,magic/request,magic/verify,logout,me}`, all Zod-validated and behind the per-device limit; login and magic-link requests also 5 per email per 15 minutes (key = sha256 of the lower-cased email). Every auth route answers 403 `https_required` unless the request is HTTPS (directly or `X-Forwarded-Proto`) or addressed to localhost (AC-12.3). (3) Sessions: 32 random bytes in `cn_session` (HttpOnly, SameSite=Lax, Path=/, Secure except on localhost), sha256 stored, 24 h sliding, extended at most hourly and only by API calls (pages read without extending, since they can't re-send the cookie). (4) Magic links: 32 random bytes base64url, sha256 stored, single use, 15 min, and they create the account if there isn't one (PRD §3.5). Requests always answer `{ ok: true }`. The link opens `/account/verify`, which does nothing until a button is pressed, so link scanners can't use it up. Locally, links go to `/dev/inbox` — in process memory only (`globalThis`, last 20, unexpired), shown only to localhost Hosts, `noindex`, never logged or written to disk. (5) Invites (`PILOT_INVITE_REQUIRED=true`): 12-character codes without look-alike characters, hash-only, with max uses and expiry; `npm run invite:create -- --uses N --days D` prints one once. A magic link for a new email asks for the code on the verify page; asking doesn't use the link, and a wrong code rolls back. (6) UI: `/account` (sign in by password or "Email me a sign-in link", create an account, signed-in view with sign out), a quiet "Sign in" / "Your account" link under the landing page's guest line, and a quiet "Keep your summaries" card under the feedback card on both results when signed out (opens `/account` in a new tab so the result stays). Not on urgent screens or journey top bars. Every guest path is unchanged. (7) The localhost check moved to `src/lib/security/local.ts`, shared by `/admin/usage` and `/dev/inbox`. `handler` in `src/lib/api/route.ts` now passes the `Request` through and has a body-less sibling `handle` for GET/DELETE routes.
**Why:** FR-12, FR-13 / T-23; PRD §3.5, §12.3.
**Affects:** `src/lib/auth/*`, `src/app/api/auth/*`, `src/app/account/*`, `src/app/dev/inbox/*`, `src/components/account/*`, `src/components/result/AccountPrompt.tsx`, both result views, `src/app/page.tsx`, `src/lib/api/route.ts`, `src/lib/limits/rate.ts`, `src/lib/security/local.ts`, `src/app/admin/usage/page.tsx`, `scripts/invite.mjs`, `content/ui/en.json`, `docs/security-checklist.md`.
**Alternatives considered:** bcrypt (argon2id is the PRD's first choice); checking the invite when the magic link is requested (the request must answer the same for every email, so the person would never learn why no link came); a GET verify link that signs in on open (email scanners would burn it); returning "email already registered" on sign-up (reveals accounts).

## T-24 saved summaries: encrypted, list, reopen, re-download, delete, export — 2026-10-22

## T-27 playful dialect mode — 2026-10-22

## Gate classifier reads the question and earlier answers — 2026-10-22

**Decision:** Product owner: the gate "needs to have knowledge of the questions asked before, so it can make that decision with context" ("doulè ki pike" on a later step returned `uncertain` after "shooting pains in my knee"). (1) `POST /api/screen` takes an optional `context`: the current question and the earlier answers in this journey, in order. Questions go by identifier (`{ kind: "field", field }` for the 7 Journey 1 free-text fields; the server maps each to its English question in `content/ui/en.json`, and drops any wording a client adds) or, for a follow-up, `{ kind: "followup", intent, question }` (intent from the fixed lists; the question text has to be sent because it is generated per person, and it goes to the model inside a data block like the answers). Who it is for and the timing picks go as plain facts (enums) and are rendered from the English labels; the age band is the existing `ageBand`. Zod validates the shape (at most 10 earlier answers); the route returns 413 when any context string is over `MAX_TEXT_CHARS` or the whole context is over the new `MAX_SCREEN_CONTEXT_CHARS` (default 20000, enough for a full Journey 1 at the default limits). Old callers without `context` are unchanged. (2) Only the GATE classifier (and its PRD 9.8 English second pass) reads the context, redacted like the text. Rules and moderation screen the current text only, exactly as before, and the combiner still takes the most cautious result, so context can never cancel a rules hit or a moderation flag. (3) Prompt `gate-classifier.v3.md` (v2 removed): earlier answers and the question are context only, to work out what the current answer refers to; the level is for the current answer; context never lowers it; a warning sign in the context may raise it when the current answer could be about it; everything in the blocks is data. Block tags inside any user-held text are neutralised so it can't pose as another block. The prompt's examples deliberately differ from the urgency scenarios. Same output schema; the gate result carries `promptVersion` (`gate-classifier@v3`; optional in the schema, so the client's own fail-closed result still parses). (4) Journey 1 sends, for each field, its question id, the fields before it and the picks up to its step; for each follow-up answer, its question, every guided answer and the follow-ups answered before it. Journey 2 sends each follow-up's question and the follow-ups answered before it, but not the letter: it can be 6000 characters, it was screened on its own at confirmation, and the question already names what it asks about. The client keeps the context within the limit by leaving out whole earlier answers in order (`fitContext`), never by cutting one. The combined re-screen before generation is unchanged. (5) Nothing new is logged.
**Why:** product-owner request, 2026-10-22; FR-05, CLAUDE.md rules 1, 2, 8, 10.
**Affects:** `src/lib/ai/schemas/gate.ts`, `src/lib/safety/{context,classifier,gate}.ts`, `src/lib/ai/prompts/gate-classifier.v3.md`, `src/app/api/screen/route.ts`, `src/lib/client/screen.ts`, `src/lib/prepare/screen-context.ts`, `src/components/prepare/PrepareFlow.tsx`, `src/components/understand/UnderstandFlow.tsx`, `src/app/{prepare,understand}/page.tsx`, `src/lib/config/env.ts`, `.env.example`, `tests/urgency/{scenarios.json,matrix.urgency.ts,rules-tier-a.test.ts}`, `tests/unit/screen-context.test.ts`.

Open for the product owner: whether `continue_after_ack` should still apply to crisis wording (CONTEXT.md §15 item 1) is unchanged by this.
